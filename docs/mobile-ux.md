# UX мобільного застосунку

UX-first: застосунок має бути максимально зручним. Тут вимірювані принципи, які обов'язкові для кожного мобільного пункту [роадмапу](roadmap.md#мобільний-застосунок) і входять у критерії приймання.

## Принципи

| Принцип | Вимога |
|---|---|
| **Мінімум тапів** | Щоденні дії мають ліміт тапів від головного екрана (таблиця нижче) |
| **Скасувати, а не підтвердити** | Замість діалогів «Ви впевнені?» — дія одразу і тост «Скасувати». Підтвердження — лише для незворотного (видалення акаунта) і для алергенів |
| **Оптимістичний UI** | Дія відображається миттєво, синхронізація — у фоні; помилка показується без втрати введеного |
| **Офлайн** | Закупка й готування повністю офлайн; решта показує кеш і зрозуміло каже, що потребує мережі |
| **Розумні значення за замовчуванням** | Підставляється те, що людина обирала минулого разу: товар, порція, частки, мережа |
| **Одна рука** | Основні дії в нижній третині екрана; у закупці й готуванні — великі цілі (≥ 56 pt) |
| **Пусті стани** | Кожен пустий екран пояснює, що тут буде, і дає кнопку наступного кроку |
| **Скелетони** | Замість спінерів на весь екран |
| **Необов'язкове — необов'язкове** | Ціна, зважування, фото ніколи не блокують сценарій; застосунок м'яко нагадує |
| **Доступність** | Динамічний розмір шрифту, VoiceOver / TalkBack, контраст WCAG AA |

## Ліміти тапів

| Дія | Ліміт |
|---|---|
| Записати з'їдене (повторна позиція чи страва з плану) | ≤ 3 |
| Позначити позицію закупки купленою | 1 |
| Наступний крок у готуванні | 1 |
| Додати продукт у запаси | ≤ 4 |
| Сканувати чек | ~~≤ 2 до камери~~ → ≤ 3 до камери: «+» → «Почати закупку» → «З чека»; в активній закупці — 1 («Додати чек» у хедері) |
| Вибрати нещодавній продукт у пікері | 1 |
| Знайти продукт пошуком | ≤ 3 + текст |
| Відкрити сканер штрихкоду в пікері | 1 |

## Чекліст для M-пункту

Кожен мобільний пункт має AC, які перевіряють:

- [ ] ліміти тапів для його щоденних дій;
- [ ] «скасувати» замість підтверджень;
- [ ] поведінку офлайн і при помилці мережі;
- [ ] значення за замовчуванням з минулих дій;
- [ ] пусті стани й скелетони;
- [ ] доступність (великий шрифт, читач екрана).

## Рішення

- Принципи як AC, а не побажання. *Чому*: «зручно» неможливо перевірити; ліміт тапів і чекліст — можна.
