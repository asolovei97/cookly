# Застосування

Як прапорці перевіряються в API, синхронізації й воркері, як клієнт дізнається про зміни і де живе глобальна мінімальна версія.

## x-feature

- Операція контракту, що належить фічі, має розширення **`x-feature: <key>`**, як `x-permission` в адмінці ([B3](../03-admin-auth/access.md#x-permission)).
- Middleware після автентифікації обчислює прапорець для контексту запиту:
  - off → **`403 feature.disabled`** з полем `feature`;
  - on, але версія застосунку нижча за `minFeatureVersion` платформи → **`426 feature.upgrade_required`** з `feature` і `minVersion`.
- Операції без `x-feature` належать ядру й перевіряються лише глобальною мінімальною версією.
- Без `X-App-Version` (адмінка, тести) версія фічі не перевіряється — як у [B1](../01-backend-bootstrap/http-and-errors.md#мінімальна-версія-застосунку).

## Версія фічі

- Кардинальна зміна фічі: сервер тримає стару й нову версію ендпоінтів поруч ([еволюція API](../01-backend-bootstrap/http-and-errors.md#еволюція-api)), а `minFeatureVersion` піднімається, коли стару пора прибрати.
- Клієнт показує «оновіть, щоб користуватися закупкою» лише на цій фічі; решта застосунку працює.

## Синхронізація

- Тип операції в реєстрі [B14](../14-offline-sync/protocol.md#реєстр-типів) оголошує свій `feature`.
- Фіча off → `rejected` з `feature.disabled`; версія застара → `rejected` з `feature.upgrade_required`.
- Такі операції **лишаються в черзі клієнта** і відправляються знову після ввімкнення чи оновлення; дані не губляться.
- Залежні операції отримують `sync.dependency_failed`, як зараз.

## Воркер

- Задача, що належить фічі (адаптер [чеків](../../receipts.md)), перевіряє прапорець у контексті своєї сім'ї.
- Фіча off → задача **пропускається** зі статусом `skipped`, без повторів; користувач бачить «фіча недоступна».

## Кеш і версія

- Прапорці й групи — у PostgreSQL. Кожен інстанс API тримає їх **у пам'яті** й обчислює прапорці без походу в БД.
- Зміна в адмінці збільшує **версію прапорців** і надсилає повідомлення в **Redis pub/sub**; інстанси перечитують правила.
- Якщо повідомлення загубилося, інстанс звіряє версію з БД раз на **30 секунд**.

## Контракт клієнта

- `GET /v1/features` → `{ version, features: { key: { enabled, variant } } }` — обчислений набір для сім'ї й акаунта.
- Без токена (`security: []`) повертаються лише [публічні прапорці](flags.md#публічні-прапорці).
- Кожна відповідь API має заголовок **`X-Features-Version`**: якщо він не збігається з кешованою версією, клієнт перезапитує `GET /v1/features`.
- Клієнт також оновлює набір на старті, при поверненні в застосунок і після `403 feature.disabled` чи `426 feature.upgrade_required`.
- Невідомий прапорець → значення з коду клієнта: `optional` — off, `core` — on ([M10](../../roadmap.md#мобільний-застосунок)).

## Глобальна мінімальна версія

- ~~`MIN_APP_VERSION_IOS`, `MIN_APP_VERSION_ANDROID` з env~~ → таблиця налаштувань, редагується в адмінці; env лишається значенням за замовчуванням, поки таблиця порожня.
- Перевірка та сама, що в [B1](../01-backend-bootstrap/http-and-errors.md#мінімальна-версія-застосунку): `426 app.upgrade_required` для всього застосунку.
- Підвищення — з причиною й підтвердженням ([небезпечні зміни](flags.md#небезпечні-зміни)).
- Значення кешується так само, як прапорці.

## Коди

| Ситуація | HTTP | `code` |
|---|---|---|
| Фіча вимкнена для контексту | 403 | `feature.disabled` |
| Версія нижча за мінімальну версію фічі | 426 | `feature.upgrade_required` |
| Правила груп чи відсотка для кор-фічі | 422 | `feature.core_rules` |
| Небезпечна зміна без причини | 422 | `feature.reason_required` |
| Невідомий ключ в адмін-запиті | 404 | `feature.not_found` |
