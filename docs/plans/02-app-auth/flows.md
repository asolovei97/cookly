# Флоу

Основні сценарії автентифікації та їхні ендпоінти.

## Ендпоінти

| Метод і шлях | Безпека | Що робить |
|---|---|---|
| `POST /v1/auth/apple` | публічний | Вхід через Apple: `idToken`, `nonce`, `authorizationCode`, дані пристрою |
| `POST /v1/auth/google` | публічний | Вхід через Google: `idToken`, `nonce`, дані пристрою |
| `POST /v1/auth/register` | публічний | Реєстрація за квитком |
| `POST /v1/auth/refresh` | публічний | Оновлення пари токенів |
| `POST /v1/auth/restore` | публічний | Відновлення акаунта за квитком відновлення |
| `POST /v1/auth/logout` | токен | Вихід з поточного пристрою |
| `GET /v1/me` / `PATCH /v1/me` | токен | Профіль; зміна імені й мови |
| `DELETE /v1/me` | токен | Запит на видалення акаунта |
| `GET /v1/me/sessions` | токен | Список сесій |
| `DELETE /v1/me/sessions/{id}` | токен | Вихід з іншого пристрою |
| `DELETE /v1/me/sessions` | токен | Вихід з усіх пристроїв |
| `POST /v1/me/identities/{provider}` | токен | Прив'язати Apple чи Google |
| `DELETE /v1/me/identities/{provider}` | токен | Відв'язати провайдера |

Дані пристрою: `deviceId` (UUID, який клієнт генерує і зберігає в Keychain / Keystore), `deviceName`, `platform` (`ios` | `android`).

## Вхід

1. Клієнт отримує `id_token` від провайдера, передавши йому `nonce`.
2. Бекенд перевіряє підпис, `iss`, `aud`, `exp` і що `nonce` ще не використано, див. [захист](protection.md#nonce).
3. Результат залежить від стану ідентичності:

| Стан | Відповідь |
|---|---|
| Ідентичність прив'язана, акаунт `active` | `200`, `status: authenticated`, пара токенів, сесія для пристрою |
| Ідентичність нова | `200`, `status: registration_required`, квиток реєстрації (10 хв) |
| Акаунт `pending_deletion` | `200`, `status: pending_deletion`, квиток відновлення; токени не видаються |
| Акаунт `suspended` до дати в майбутньому | `403 auth.account_suspended` з `until`; сесії відкликаються |

Вхід з того самого пристрою відкликає попередню сесію цього користувача на ньому, див. [сесії](tokens-and-sessions.md#сесії).

## Реєстрація

`POST /v1/auth/register` приймає:

- квиток реєстрації;
- `displayName` — 2–30 символів після trim, без заборонених слів, див. [фільтр імен](protection.md#фільтр-імен);
- мову: `uk` | `en`;
- рік народження — вік має бути від 16 років;
- згоду: версії умов і політики приватності, які прийняв користувач. Бекенд зберігає їх із датою.

Успіх: створюються акаунт (`active`, `householdId: null`), ідентичність і сесія; повертається `status: authenticated` з токенами. Далі клієнт веде на онбординг сім'ї ([B5](../../roadmap.md#бекенд)).

Помилки:
- вік до 16 → `403 auth.age_restricted`, квиток стає недійсним;
- некоректне ім'я → `422` з `errors[]` для `/displayName`: довжина за контрактом — `request.invalid`, довжина після trim чи заборонене слово — `auth.invalid_name`; квиток лишається чинним;
- без згоди → `422 request.invalid`;
- квиток прострочений або використаний → `401 auth.ticket_expired`.

## Прив'язка провайдерів

- Залогінений користувач прив'язує другий провайдер, щоб входити з іншої платформи в той самий акаунт.
- Ідентичність уже належить іншому акаунту → `409 auth.identity_taken`, нічого не об'єднується.
- **Автоматичного злиття за email немає.** Якщо користувач входить провайдером, якого ще немає в акаунті, він отримує `registration_required`. Клієнт може підказати: «увійдіть старим способом і прив'яжіть цей провайдер у налаштуваннях».
- Відв'язати останнього провайдера не можна → `409 auth.last_identity`.
- Під час відв'язки Apple токен відкликається в Apple, див. [токени Apple](tokens-and-sessions.md#токени-apple).

## Видалення й відновлення

1. `DELETE /v1/me` → статус `pending_deletion`, усі сесії відкликаються, `202`.
2. Протягом 30 днів вхід повертає `status: pending_deletion` з квитком відновлення.
3. `POST /v1/auth/restore` з квитком → статус `active`, токени нової сесії.
4. Після 30 днів анонімізацію виконує воркер — [B19](../../roadmap.md#бекенд). Що буває з персоною в сім'ї — у [приватності](../../accounts/privacy.md).
