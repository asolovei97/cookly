# Протокол

Як клієнт відправляє операції і дізнається про зміни з інших пристроїв.

## Операція

```json
{
  "opId": "0192…",            // UUIDv7, згенерований клієнтом
  "type": "pantry.delta@1",   // тип і версія
  "entityId": "0192…",        // UUIDv7 сутності, зокрема створеної офлайн
  "payload": { … },
  "clientTime": "2026-11-04T18:20:00Z"
}
```

## Реєстр типів

- Домен **реєструє тип**: схему `payload`, обробник (той самий доменний сервіс, що й онлайн-API, з тією самою валідацією) і які сутності повертати в стані.
- У B14: `pantry.delta@1`, `catalog.product.create@1`, `catalog.ingredient.create@1`.
- Закупка й готування реєструють свої типи в [B15](../../roadmap.md#бекенд) і [B16](../../roadmap.md#бекенд).
- Нова версія типу (`@2`) додається поруч зі старою; стара підтримується, поки її надсилають підтримувані версії застосунку ([еволюція API](../01-backend-bootstrap/http-and-errors.md#еволюція-api)).
- Невідомий тип → `rejected` з `sync.unsupported_op`.

## Відправка

`POST /v1/sync/ops` з пакетом операцій.

- Сервер бере **блокування на сім'ю** і застосовує операції **послідовно** в порядку пакета (порядок створення на пристрої).
- Кожна операція — у власній транзакції: відхилення однієї не відкочує попередні.
- Відповідь для кожної операції:

| Статус | Значення |
|---|---|
| `applied` | Застосовано |
| `duplicate` | `opId` уже бачили; повертається збережений результат |
| `rejected` | Не застосовано; `code` — доменний код помилки або `sync.*` |

- Разом з результатами — **актуальний стан** зачеплених сутностей і новий курсор.

## Залежні операції

- Операція може посилатися на сутність, створену попередньою операцією того самого пакета чи попередніх пакетів (новий товар → позиція закупки з ним).
- Якщо операцію, від якої залежить наступна, відхилено, залежна отримує `rejected` з `sync.dependency_failed`.

## Зміни з інших пристроїв

`GET /v1/sync/changes?since=<cursor>`

- **Журнал змін сім'ї**: кожна зміна офлайн-сутностей (сесії закупки й готування, запаси, створені офлайн товари) отримує номер у послідовності сім'ї.
- Відповідь — зміни після курсора (актуальний стан сутностей, а не операції) і новий курсор.
- Повертаються лише сутності своєї сім'ї.
- Клієнт викликає після кожної відправки і періодично, поки сесія відкрита.

## Дублікати

- `opId` і результат зберігаються **90 днів**; повтор у цьому вікні → `duplicate`.
- Очищення — задача воркера.

## Час

- `clientTime` — коли дію зробили на пристрої. Іде в історію запасів і стає датою [спостереження ціни](../08-prices/observations.md).
- Приймається, якщо він не в майбутньому (запас 5 хвилин) і не старший за 7 днів; інакше береться час сервера.
- **Порядок застосування** визначає сервер, а не `clientTime`.

## Межі

- Пакет — до **500 операцій** або **1 МБ** → інакше `413 sync.batch_too_large`.
- Операції з сутностями іншої сім'ї → `rejected` з `sync.not_found`.
- Ендпоінти вимагають access-токен ([B2](../02-app-auth/tokens-and-sessions.md)); автор операції — акаунт з токена.
