# Сесії

Як адмін входить, як живе його сесія і як захищено адмін-API.

## Вхід

1. Адмін вводить email і пароль.
2. Потім — код TOTP або код відновлення.
3. Успіх → створюється сесія, браузер отримує cookie.

Будь-яка помилка (немає email, неправильний пароль чи код) → `401 admin.invalid_credentials`. Відповідь не розкриває, чи існує такий email.

## Захист входу

- **5 невдалих спроб** поспіль → акаунт блокується на **15 хвилин**: `429 admin.locked` з `Retry-After`.
- **Ліміт запитів з IP** на ендпоінти входу.
- Значення задаються в конфігу.

## Cookie-сесії

- Сесія зберігається **на сервері, в PostgreSQL**. Cookie містить лише її ідентифікатор.
- Атрибути cookie: `HttpOnly`, `Secure`, `SameSite=Strict`.
- **Захист від CSRF**: запити, що змінюють дані, несуть CSRF-токен; без нього чи з невалідним → `403 admin.csrf_invalid`.
- Строки:
  - **30 хвилин** бездіяльності;
  - **12 годин** абсолютний строк.
  Прострочена сесія → `401 admin.session_expired`.
- Сесії адміна відкликаються **миттєво**, коли його деактивують або скидають йому 2FA.
- Вихід видаляє сесію на сервері.

## Адмін-API

- Той самий бінарник `api`, префікс **`/admin/v1`**.
- **Окремий файл контракту** і окремий TS-клієнт для [адмінки](../../admin.md).
- Схема безпеки — `cookieAuth`.
- **CORS** дозволений лише для домену адмінки.
- У production адмін-API можна винести на окремий хост чи порт і закрити мережевими правилами — вирішимо в P2.
