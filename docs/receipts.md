# Чеки

Імпорт фіскального чека за QR-кодом: позиції стають спостереженнями цін, поповненням запасів і фактом бюджету без ручного введення.

## Сценарій

1. Користувач сканує QR-код чека в застосунку.
2. Застосунок надсилає на сервер **лише URL** з QR. Офлайн URL чекає в черзі [синхронізації](tech-decisions.md#офлайн).
3. Воркер обирає **адаптер за доменом**, завантажує сторінку чека й розбирає її.
4. Застосунок показує **прев'ю**: рядки чека, зіставлені з каталогом, і рядки, які треба зіставити вручну.
5. Користувач підтверджує, і чек:
   - створює [спостереження цін](prices/observations.md) на кожен рядок (ціна за одиницю, мережа, місто з адреси магазину);
   - поповнює [запаси](pantry.md) дельтами;
   - іде у факт [бюджету](planning/budget.md).

## Режими

- **Прикріпити до активної [закупки](shopping.md)**: збіглі позиції позначаються купленими з фактичною ціною, решта додається як позиції поза списком. Якщо закупка активна, застосунок пропонує саме це.
- **Окрема «закупка з чека»**: якщо активної закупки немає.

## Адаптери

| Джерело | Що дає | Статус |
|---|---|---|
| `receipt.silpo.elkasa.com.ua` (Сільпо) | Серверний HTML: магазин, адреса, дата, фіскальний номер, рядки (штрихкод, назва, кількість × ціна, сума), знижка | **MVP** |
| `cabinet.tax.gov.ua/cashregs/check` (ДПС) | Невідомо: це JS-застосунок | **MVP, якщо spike підтвердить** позиції без капчі |
| Фото паперового чека (OCR на пристрої) | Обрізані назви, низька точність | [Майбутнє](future.md) |

- Адаптер — код у воркері за спільним інтерфейсом; нова мережа = новий адаптер.
- Розбір HTML — мілісекунди, без LLM і без машинного зору.

## Зіставлення рядків

Назви в чеках обрізані (`КурячеКгФіле`), а вагові товари мають внутрішній код мережі замість штрихкоду. Порядок:

1. **Штрихкод** → товар з цим штрихкодом.
2. Інакше **аліас мережі**: (мережа, код або назва з чека) → товар чи інгредієнт.
3. Інакше користувач обирає інгредієнт або **створює товар** на його основі ([каталог](catalog/ingredients-and-products.md#заміна-якщо-потрібного-товару-немає)), і це зіставлення стає аліасом.

- Аліас одразу працює для сім'ї.
- Для всіх — після [модерації](catalog/moderation.md) або автоматично, коли **3 сім'ї** незалежно зіставили однаково.
- Кількість: дробова кількість (`0.252 X 189.00`) — вага в кг; ціле число — штуки чи упаковки.

## Приватність

- **Платіжні дані** (маскована картка, RRN, код авторизації, термінал) і дані **програми лояльності** вирізаються до запису.
- Зберігаються: мережа, адреса магазину, дата, id чека, розібрані рядки.
- **Сирий HTML** — 30 днів, лише для налагодження адаптерів, без доступу клієнтів.

## Рішення

- Парсинг на сервері. *Чому*: адаптери оновлюються без релізу застосунку, дедуплікація за id чека, кеш і ліміт частоти на домен. Навантаження мізерне — один HTTP-запит і розбір HTML. *Відкинуто*: парсинг на пристрої — кожна зміна верстки мережі потребує оновлення застосунку.
- QR-шлях замість OCR. *Чому*: структуровані дані з першоджерела; OCR на обрізаних назвах і поганому друці ненадійний.
- Підтвердження через прев'ю. *Чому*: зіставлення може помилятися, а запаси й ціни мають бути правдивими.

## Граничні випадки

- Той самий чек імпортують двічі (зокрема інший учасник сім'ї) → дедуплікація за доменом і id чека, повторний імпорт відхиляється.
- Домен невідомий → «цей чек поки не підтримується»; URL зберігається для статистики, які мережі додавати.
- Сторінка недоступна → повтори у воркері; користувач бачить «чек обробляється».
- Знижка на весь чек розподіляється між рядками пропорційно сумі, щоб ціна за одиницю відповідала сплаченому.
